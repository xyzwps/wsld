# 双语文案与词条的依据

## 为什么要有 Localizer

文案烧在 XAML 里意味着"想换语言就得改代码重编译"。`wslc` 本身就有中英文两套输出,
界面跟着系统显示语言走才不别扭。所以全应用文案集中成中英两套键值(009 那次抽取是 125 个键,
010 加 10 个、011 加 2 个 `pull.*`、012 加一批 `run.*`,只增不减)。

## 四条钉住的纪律

| 纪律 | 说明 |
|---|---|
| 两套键集合**完全一致** | 中文有的键英文必须有,反之也一样;新增功能必须一次加齐两套 |
| **占位符一致** | 同一条键的两份文案里 `{0}` / `{1}` 数量与含义要对得上 |
| **不允许空值** | 两边都不留空串 |
| 以上三条**有测试钉住** | `LocalizerTests` 遍历两套键做比对,漏一个直接红 |

缺键时的兜底:退回中文;中文也没有就把**键名原样显示**出来,让漏翻一眼看得见 —— 不静默显示空白。

## 跟随系统的判定

三档:跟随系统 / 简体中文 / English。跟随系统 = `CultureInfo.CurrentUICulture` 的两字母代码是 `zh`
就取中文,**其余一律 fallback 到英文**。

## 数字与日期

- 日期、数字按 `zh-CN` / `en-US` 报 locale,但 `Fmt` 内部格式化数字用 `InvariantCulture` ——
  界面数字不跟着线程 culture 乱跳。
- `string.Format(InvariantCulture, "{0}", 1000)` 出来是 `1000`,**不带千分位**(默认 G 格式),
  所以列表里是"最近 1000 行"而不是"最近 1,000 行"。估条目宽度时按不带逗号算
  → 见 dev-notes 第 23 条。

## 换语言为什么要整页重建、还要排队到下一帧

`Localizer.LanguageChanged` 之后分两步:先 `ApplyTexts()`(导航项、tooltip、页标题这类代码里赋的文案),
再 `RebuildPages()` 整页重建 —— **静态文案烧在页面里,只有重建才换得干净**。

重建必须排队到下一帧:语言单选按钮的 `Checked` 事件还在调用栈上,当场拆可视树不安全。
重建前若日志页正在跟随,先 `CancelFollow()` —— 不能留下一个没人看的孤儿 `wslc` 进程。

顺带一条:下拉框候选项这类本地化文案在页面构造时把数组拼好就够,切换语言时主窗口会重建页面跟着取一次
(内联 `ComboBoxItem` 绑内容会出问题,见 dev-notes 第 39 条)。

## 测试语言为什么要钉住

001–005 的 242 项断言写的都是改版前的**中文原句**。靠 `TestEnvironment` 的 `[ModuleInitializer]`
把测试语言钉成简体中文 —— 否则测试结果会跟着测试机器的系统语言变。
文案抽取本身不改变任何业务行为,这正是这批回归的意义。

## 中英两套文案的宽度可以不对称

改版时为了让英文一行塞得下,英文表改成 `200 lines` / `Timestamps`(原 `Last 200 lines` / `Show timestamps`),
而**中文表刻意保持与改版前逐字一致** —— 001–005 的断言依赖它。
这是"英文可以改短、中文不许顺手改"的一条历史约定,动词条前先想清楚会不会打到既有断言。

纯图标按钮的 `ToolTip` 和 `AutomationProperties.Name` 都走 Localizer,少一个就是
"换语言后残留另一种语言" —— 见 `winui-shell.md`。

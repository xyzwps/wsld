# container-actions

## Purpose
对单个容器做的四个动作:启动 / 停止 / 重启 / 删除。行上只有一颗"启动"键,其余三颗在选中后的详情头部
(键的出现与长相归 `container-detail.md`,CD)。错误文案的清洗与 `container-list.md` 的 CL-018、CL-019
是同一套规矩,那边已写死,这里不重复、只引用。

### Requirement: 四颗键与 `wslc` 子命令一一对应,认 ID 不认名字
启动/停止/重启/删除分别就是 `start` / `stop` / `restart` / `remove`,参数是容器 12 位 ID 加动作本身,
不带别的选项;删除正在运行的容器必须 `-f`(依据见 `docs/notes/wslc-cli.md`)。

#### Scenario: CA-001 启动只发一条 `start <ID>`
- **WHEN** 按下一行或详情头部的「启动」
- **THEN** wslc 那侧收到的命令行是 `start <12位ID>`,除此之外不多发一条

#### Scenario: CA-002 停止只发一条 `stop <ID>`
- **WHEN** 按下一颗「停止」
- **THEN** wslc 收到的命令行是 `stop <12位ID>`,没有 kill、没有超时参数、没有第二个进程

#### Scenario: CA-003 重启只发一条 `restart <ID>`
- **WHEN** 按下一颗「重启」
- **THEN** wslc 收到的命令行是 `restart <12位ID>`

#### Scenario: CA-004 删除对已停止的容器发 `remove <ID>`
- **WHEN** 容器已停止,在确认框里点了「删除」
- **THEN** wslc 收到的命令行是 `remove <12位ID>`,不带 `-f`

#### Scenario: CA-005 删除对运行中的容器发 `remove -f <ID>`
- **WHEN** 容器正在运行,在确认框里点了「删除」
- **THEN** wslc 收到的命令行是 `remove -f <12位ID>` —— 不加 `-f` 会被引擎以"容器正在运行"拒绝

#### Scenario: CA-006 用 ID 不用名称
- **WHEN** 发起上述任何一条命令
- **THEN** 命令行里的容器参数永远是 12 位 ID,不是界面上更顺眼的容器名称
- **AND** 容器没有名称(靠 ID 认)时操作照常,发的还是那个 ID

### Requirement: ID 拿不到就一步都不迈
容器标识为空或只有空白时,四个动作谁都不许起进程。

#### Scenario: CA-007 空 ID 不发任何命令
- **WHEN** 某个动作在没有可用容器 ID 的情况下被触发(容器已经不在列表里)
- **THEN** wslc 那侧一条命令都没收到,连进程都不起
- **AND** 界面停在原地,不崩、不冒出半截状态

### Requirement: 全局一次只有一个动作在飞
同一时刻整个页面只允许一个生命周期操作;第二次触发直接被忽略,不排队、不叠加。

#### Scenario: CA-008 操作进行中,所有操作键一律按不动
- **WHEN** 有一次启动/停止/重启/删除正在进行(不管是行上还是详情头部触发的)
- **THEN** 每一行的「启动」与详情头部四颗键全部变灰,点不动
- **AND** 发起操作的那一行同时转起忙碌圈

#### Scenario: CA-009 二次触发被吞掉,wslc 只听见一条命令
- **WHEN** 一次操作还没结束,又去点第二颗(或狂点同一颗)
- **THEN** 第二次触发不产生任何 wslc 调用,界面上也不报错
- **AND** 第一个操作结束后,按钮统一恢复可用

### Requirement: 操作进行中列表保持安静
动作在飞的时候不读列表,免得界面在操作中途被换血、用户看到不上不下的中间态
(与 CL-010 是同一件事的两面:CL 说的是列表不刷,这里说的是操作按下的那几秒)。

#### Scenario: CA-010 操作期间不发出 `wslc list`
- **WHEN** 一次操作正进行中,自动刷新节奏到点,或者用户点了「刷新」
- **THEN** 期间一条 `wslc list` 都不发,wslc 只听见那一次操作命令
- **AND** 操作结束(成败都一样)后,列表照旧能刷

### Requirement: 成功就刷一次,失败就原地站着
wslc 的这四个命令成功时静默(退出码 0、无输出),失败时 stderr + 非 0;界面跟着这个分工走(依据见
`docs/notes/wslc-cli.md`)。

#### Scenario: CA-011 操作成功 → 列表刷新一次,状态跟着变
- **WHEN** 一次操作以退出码 0 结束
- **THEN** 界面只补发一次 `list -a --format json`,列表、汇总数字、"最近刷新"时刻随之更新
- **AND** 那一行与详情头部的新状态同批出现:启动后读得到"运行中",停止后读得到"已停止"

#### Scenario: CA-012 删除成功 → 那一行消失,详情区收回
- **WHEN** 删除操作成功
- **THEN** 刷新之后这个容器从列表里消失,一行不剩
- **AND** 右栏详情回到空状态提示语(见 CD-001),它的日志会话跟着收摊(见 LG)

#### Scenario: CA-013 操作失败 → 不刷新,旧数据原样留着
- **WHEN** 一次操作以非 0 退出码失败
- **THEN** 界面不补发任何 `wslc list`,列表还是上一次成功读回的样子
- **AND** 错误条挂出清洗后的文案(同一套规矩见 CL-018;stderr 为空时是"wslc 命令执行失败。",见 CL-019)
- **AND** 下一次自动刷新一到,错误条消失、列表照常更新

#### Scenario: CA-014 引擎拒绝要说清是谁
- **WHEN** 一次删除因容器正在运行被引擎拒绝(stderr 里有错误描述与 `错误代码:` 一行)
- **THEN** 错误条读得到那句描述与错误代码那一行,一行连成一句
- **AND** 读不到"欢迎提 issue"那句样板话

### Requirement: 按钮可用性只是体验优化
wslc 的启动/停止对状态重复的调用返回退出码 0,重启会把已停止的容器直接启动 —— 可用性规则
不是正确性前提(依据见 `docs/notes/wslc-cli.md`)。

#### Scenario: CA-015 运行中的容器,「启动」按不动
- **WHEN** 选中的容器正在运行
- **THEN** 详情头部的「启动」是灰的,「停止」可按

#### Scenario: CA-016 已停止的容器,「停止」按不动
- **WHEN** 选中的容器已停止
- **THEN** 详情头部的「停止」是灰的,行上的「启动」可按

#### Scenario: CA-017 「重启」与「删除」永远可按
- **WHEN** 容器任意状态下被选中
- **THEN** 「重启」「删除」都可按;对已停止的容器点「重启」,它会被直接启动

### Requirement: 会打断容器里跑着的东西,先问一句
停止 / 重启 / 删除都算危险动作,点下去之前各弹一个确认框;「启动」不打断任何东西,照旧一键就走。
Core 层不做任何确认;确认只在界面上弹对话框。对话框必须正常弹出、不崩 —— 不崩的缘由是一处
非打包模式下的坑,记在 `docs/dev-notes.md` 第 16 条,那是实现要守的,不是用户能看见的契约。

#### Scenario: CA-018 点删除先弹确认框(已停止的措辞)
- **WHEN** 对一个已停止的容器点「删除」
- **THEN** 弹出标题为"删除容器"的对话框,正文读得到"确定要删除容器 <名称>?此操作不可恢复。"
- **AND** 两个按钮读得到「删除」与「取消」,焦点默认落在一键下去什么都不发生的动作上

#### Scenario: CA-019 运行中的容器多一句红字
- **WHEN** 对一个正在运行的容器点「删除」
- **THEN** 对话框除了上面那句,还多一行"该容器正在运行,将强制停止并删除(wslc remove -f)。"
- **AND** 确认框弹出的那一刻就按运行/已停止决定措辞,之后容器状态变了也不改口

#### Scenario: CA-020 点「取消」什么都不发生
- **WHEN** 对话框弹出后点「取消」(或按 Esc 关掉它)
- **THEN** 对话框收起,wslc 一条命令都没收到,列表与详情纹丝不动

#### Scenario: CA-021 点「删除」才真的删
- **WHEN** 对话框里点「删除」
- **THEN** 这时才发出对应的 remove 命令(见 CA-004、CA-005),后续成败走 CA-011–CA-014

#### Scenario: CA-022 确认框弹出时不动选中、不晃详情
- **WHEN** 确认框弹出又收起
- **THEN** 左栏选中行与右栏详情从头到尾没换过、没清空过
- **AND** 无论列表正在自动刷新还是空闲,框都正常弹出、正常收起,应用不崩

#### Scenario: CA-026 点「停止」先弹确认框
- **WHEN** 对一个正在运行的容器点「停止」
- **THEN** 弹出标题为"停止容器"的对话框,正文读得到"确定要停止容器 <名称>?容器里正在跑的进程会被终止(wslc stop)。"
- **AND** 两个按钮读得到「停止」与「取消」,焦点默认落在一键下去什么都不发生的动作上
- **AND** 点「停止」才发出 `stop <ID>`(见 CA-002),点「取消」什么都不发生(见 CA-020)

#### Scenario: CA-027 点「重启」先弹确认框
- **WHEN** 对任意状态的容器点「重启」
- **THEN** 弹出标题为"重启容器"的对话框,正文读得到"确定要重启容器 <名称>?重启期间容器里的进程会中断(wslc restart)。"
- **AND** 点「重启」才发出 `restart <ID>`(见 CA-003),点「取消」什么都不发生(见 CA-020)

#### Scenario: CA-028 「启动」不问一句
- **WHEN** 点「启动」
- **THEN** 不弹确认框,直接发出 `start <ID>`(见 CA-001)

### Requirement: 行是认 ID 续用的,不是每次重建
刷新时按容器 ID 续用同一行对象,只换数据 —— 行上的忙碌状态与按钮得活得过刷新。

#### Scenario: CA-023 按钮不闪断
- **WHEN** 列表刷新前后容器都还在
- **THEN** 每一行还是"那一行":行不消失不重建、滚动位置不动,按钮不闪断
- **AND** 状态变了(比如启动成功)时只有徽标、状态文字和按钮可用性跟着换

#### Scenario: CA-024 操作中途的自动刷新不踩状态
- **WHEN** 行上"启动"正在进行中,自动刷新一到
- **THEN** 这一行的忙碌圈照常转到操作结束,不闪断、不提前熄灭
- **AND** 期间列表本来就不刷(见 CA-010),用户不会看到操作做一半状态被打断

### Requirement: 界面只给这四个动作
没有 kill 键、没有多容器批量 —— 这是刻意留的边界,界面不该让人找得到入口。

#### Scenario: CA-025 找不到 kill,也找不到批量
- **WHEN** 把容器页行上、详情头部翻个遍
- **THEN** 读不到任何"强杀 / kill"字样的键或菜单项
- **AND** 勾选多行做批量操作在界面上无处下手,所有操作都是对一个容器一个一个来

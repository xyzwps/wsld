# 功能 005 · 容器日志

状态:已完成(2026-10-12,含真机验证)
相关:功能 001 / 002(容器列表与生命周期)、功能 003 / 004(左侧导航、可取消的长任务)

## 是什么

在左侧导航新增第三页"日志",用来读某个容器的标准输出:

1. 下拉选一个容器(名称 · 短 ID · 运行状态),可以点"刷新容器列表"重新拉;
2. 选要看的行数(100 / **200 默认** / 500 / 1000 / 2000 / 全部),可勾"显示时间戳";
3. 点"加载日志" → 一次性把日志取回来显示在等宽文本区;
4. 勾上"实时跟随"再加载 → 应用持续接收新产生的日志行并追加、自动滚到底,
   期间按钮变成"停止跟随",随时可以停;
5. 日志区只读、不换行(横向滚动),"自动滚动"可以关掉以便翻看历史。

## 为什么

容器出问题时,第一个要问的永远是"它到底打印了什么"。命令行做这件事很别扭:

- 得先 `wslc list` 抄容器名或 ID,再回来敲 `wslc logs`;
- `tail` 行数、时间戳都要自己拼参数,记不住;
- 想持续观察只能开个终端挂着 `-f`,窗口一关不知道有没有留下半死的进程;
- 已停止 / 从未启动的容器 `logs` 返回**空输出但退出码 0**,在终端里和"命令失败"看上去差不多,
  很容易误判成"日志被清掉了"。

所以这一页要提供的是:选容器不用抄名字、行数与时间戳变成两个开关、
实时跟随可以干净地开始和停止,并且**把"这个容器没有输出"和"读取失败"明确区分开**。

## 实测到的 wslc 行为(3.0.1,本规格的依据)

`wslc logs [选项] <container-id>`(别名 `wslc container logs`),选项只有
`--details`、`-f/--follow`、`-n/--tail`、`-t/--timestamps`、`--since`、`--until`,**没有 `--format json`**。

| 场景 | 实测结果 |
|---|---|
| `logs <运行中的容器>` | 退出码 0,stdout 是原始文本行(`log line 1 at 1791804984` …),行尾只有 LF |
| 用名称 / 短 ID / 长 ID | 都可以(`logs probe1`、`logs f47fdddf9219` 都是退出码 0) |
| `logs <已退出的容器>`(probe1) | **退出码 0 + 空输出**,不报错 |
| `logs <从未启动的容器>`(probe2,Created) | **退出码 0 + 空输出**,不报错 |
| `logs <不存在的容器>` | 退出码 1;stderr:`找不到容器 'nosuchcontainer'。` + `错误代码: WSLC_E_CONTAINER_NOT_FOUND` + 样板句 |
| `logs -n 3` | 退出码 0,只给最后 3 行 |
| `logs -n 1000000`(超出实际行数) | 退出码 0,不报错 |
| **`logs -n 0` / `-n -1` / `-n abc`** | 退出码 **1**;stderr 首行 `tail 选项值无效: 0` / `abc` + 8 行 usage;**stdout 为空** |
| `logs --since abc` | 退出码 1;`since 选项值无效:“abc”。预期为 Unix epoch 时间戳或 RFC3339 日期时间` + usage |
| `logs -q` | 退出码 1;`无法识别当前命令的选项别名:“-q”` + usage(`logs` 没有 `-q`) |
| `logs -t` | 每行前缀 RFC3339 **UTC 纳秒** + 空格:`2026-10-12T11:34:46.874570304Z log line 146 at ...` |
| `logs --details -n 2` | 退出码 0,但每行**多前置一个空格**(没有额外信息,本功能不用) |
| **`logs -f` 的输出时机** | stdout 重定向到文件后每 2 秒稳定增长 54 字节(容器每秒 1 行),**是真流式**,与功能 004 的 `pull`(退出才一次性冲刷)完全不同 |
| `logs -f` 的起始位置 | 不带 `-n` 时会**先把全部历史**冲出来再持续追加 → 跟随必须配 `-n` 限制起始行数 |
| `logs -f <已停止的容器>` | 立刻结束,退出码 0,stdout / stderr 全空(不报错也不提示) |
| `logs -f <从未启动的容器>` | 同上:立刻结束,退出码 0,空输出 |
| **跟随时容器被停止** | ≤2 秒内 wslc 自己退出,退出码 0,stderr 空,**没有任何"容器已结束"的提示行** |
| 跟随途中结束 wslc 进程 | 用整棵进程树终止,之后 `Get-Process wslc` 为 0 个,无残留 |

要点:

- 空输出 + 退出码 0 是 wslc 的正常语义("这容器没打印东西"),**界面不能报成错误**;
- 参数非法也是退出码 1 且文案走 stderr,并且带 8 行 usage 噪音 → 应用必须自己在发命令前把行数校验好,
  万一还是拿到 usage 类输出,展示前要用 `WslcError.Describe` 清洗;
- `-t` 给的是 UTC 纳秒串,又长又难读 → 界面在本地转成 `HH:mm:ss.fff` 显示,解析不了就原样保留;
- 跟随会"自然结束"且不留原因 → 界面自己负责说明"跟随已结束(容器多半已停止)"。
## 预期行为(验收条件)

### AC1 · 命令映射
`LogsService` 拼出的参数严格是 `logs` + 可选 `-f` + 可选 `-t` + 可选 `-n <行数>` + 容器标识,顺序固定。
行数选"全部"(值为 0)时**不发** `-n`。容器标识先 `Trim`。

### AC2 · 输入校验在启动进程之前
容器标识为 null / 全空白、行数 < 0、行数 > 100000 之一 → 抛 `ArgumentException`,
并且 `IWslcCli` **一次都没被调用**(实测 `-n 0` 只会换回 8 行 usage,没有任何价值)。

### AC3 · 文本 → 行
`WslcLogText.Split`:按 LF 拆行,去掉每行结尾的 CR,丢掉末尾的空行;
null / 空白输入 → 空数组;中间的空行要保留(那确实是日志的一部分)。

### AC4 · 行 → 界面文本
`WslcLogText.Join` 用 CRLF 拼接(只读文本框需要 `\r\n` 才换行);
单行超过 4000 个字符时截断并追加 `…(本行过长,已截断显示)`。

### AC5 · 时间戳可读化
仅当本次请求带了 `-t`:行首若是可解析的 RFC3339 / ISO8601 时间戳(含 `Z` 或 `+08:00` 后缀),
替换成**本地时间** `HH:mm:ss.fff`,该行其余内容原样保留;
解析失败或行首不是时间戳 → 整行原样;未开启时间戳选项 → 绝不改动行内容(哪怕它长得像时间戳)。

### AC6 · 错误与清洗
退出码非 0 → 抛 `WslcCliException`,`Command` 为 `wslc logs`;
界面用 `WslcError.Describe` 得到单句文案(去掉"欢迎提 issue"样板句)。

### AC7 · 跟随必须是流式
`RunLinesAsync` 每读到一行**立刻**回调(不等进程结束),同时把行累计进返回快照;
调用方回调里抛出的异常不能把读循环带崩,要转成一次错误结果。
实测依据:`logs -f` 每 2 秒稳定增长,所以"实时跟随"确实做得到。

### AC8 · 取消跟随
取消令牌触发后终止整棵子进程树并抛 `OperationCanceledException`;
**已经显示出来的日志不清空**(实测:终止跟随不会在容器里留下任何东西)。

### AC9 · 单进程互斥
同一时刻最多一个日志进程。加载 / 跟随进行中:`CanLoad == false`、
"刷新容器列表"被忽略、选项(容器、行数、时间戳、跟随)不可修改;重复调用直接返回。

### AC10 · 空日志不是错误
读取成功但 0 行 → 不设置 `Error`,`Notice` 为"容器 X 没有日志输出…",日志区清空。
这是实测里"已退出 / 从未启动的容器 → 退出码 0 + 空输出"的直接对应。

### AC11 · 只有运行中的容器可以跟随
选中非运行中的容器时 `CanFollow == false`,并把已勾选的"实时跟随"自动取消
(实测:对停止的容器 `logs -f` 会立刻结束且毫无提示,只会让人以为按钮坏了)。

### AC12 · 行先进缓冲,批量上屏
后台读线程只往线程安全队列里塞行(`EnqueueLine`),由界面计时器或攒够 64 行时 `DrainPending()`
一次性合并到 `LogText`。这样高频跟随不会每来一行就重绘一次整块文本。
单元测试直接调用 `DrainPending()`,不依赖真实时钟。

两个方向都要守住:
- **攒批**:`EnqueueLine` 只在缓冲达到 64 行时催一次上屏(AC12 的初衷,避免重绘风暴);
- **催屏**:跟随期间页面用 `DispatcherQueueTimer` 每 500ms 调一次 `DrainPending()`,
  计时器只在 `IsFollowing` 为真时运行、页面卸载即停。
  实测依据:真机上每秒只打印 1 行的容器,8 秒都攒不满 64 行,
  没有催屏计时器时状态栏会一直停在加载那一刻的行数,用户会以为"实时跟随"没生效。
  `DrainPending_AppliesEvenASingleLine` 钉住"哪怕只有 1 行缓冲也要能上屏"这个契约。

### AC13 · 显示上限与丢弃计数
界面最多保留 2000 行,超出时丢弃最早的并累计 `DroppedLineCount`,
状态栏文案包含"已丢弃最早的 N 行"。

跟随时状态栏的"最近加载"要**跟着新行一起推进**(真机验证发现:行数在涨、时间不动,
读起来就像"从那一刻起再没有新日志")。一次性读取不受这条影响。
测试:`Follow_KeepsLastLoadedTextFresh`。

### AC14 · 跟随自然结束
进程自己结束(wslc 在容器停止时就是这样)→ `IsFollowing == false`,
`Notice` 说明"跟随已结束(容器多半已停止)· 共 N 行",日志保留。

### AC15 · 容器下拉
来源列表复用功能 001 的 `ContainersService.ListAsync`,每项文案"名称 · 短ID · 运行中/已停止";
排序沿用"运行中的在前 + 名称字母序";点"刷新容器列表"后**按 Id 保留当前选择**;
读取失败只走 `Error`,不清空已有选项。

### AC16 · 界面
第三页导航标题"日志";日志区是只读等宽文本框、不换行(横向滚动)、可全选复制;
"自动滚动"默认勾选,勾掉后新行仍进入缓冲但视图位置不再被强拉到底部;
错误用红色 InfoBar、提示用绿色 InfoBar;状态栏显示"行数 · 最近加载时间 · 跟随状态"。

### AC17 · 不破坏已有功能
`IWslcCli` 新增 `RunLinesAsync` 之后,功能 001–004 的调用路径与行为完全不变;
容器页、镜像页回归通过。

### 真机验证暴露并已修复的三个问题

1. **取消被报成失败**:终止 `wslc` 后它以退出码 `-1` 自己退场,与取消信号先后是竞态,
   导致"停止跟随"偶发弹红色错误条。`ProcessWslcCli` 现在在等待退出前后各查一次取消令牌,
   令牌已触发就归一为 `OperationCanceledException`(开发笔记 #17)。
2. **工具栏被裁切**:1180 宽窗口下"自动滚动""停止跟随"被右边缘切掉。WinUI 3 没有 `WrapPanel`,
   改为"按钮占 `Auto` 列 + 下拉占 `*` 列并限宽 + 开关去掉默认 154 最小宽度"的布局约定(开发笔记 #18)。
3. **慢速日志看起来卡住**:攒够 64 行才上屏的策略,对"每秒 1 行"的容器等于 64 秒不刷新;
   跟随期间改由页面 500ms 催屏计时器驱动,并让状态栏时间随新行推进(开发笔记 #19 / #20)。

# 功能 002 · 容器生命周期操作

状态:已实现
相关:功能 001(容器列表)

## 是什么

提供 **启动 / 停止 / 重启 / 删除** 四个操作,直接调用对应的 `wslc` 子命令,并在操作完成后自动刷新列表。
入口分两处:列表行内只放"启动"(已停止的容器最常干的一件事),停止 / 重启 / 删除放在选中该容器后的详情面板 ——
四个图标按钮挤在定宽的行里会把名字顶没,而点一行本来就会把它的详情打开。

## 为什么

功能 001 只能"看"。日常使用中最频繁的动作就是停掉一个跑偏的容器、重启一个改完配置的服务、
删掉用完的临时容器。没有这些操作,这个应用就只是一个 `wslc list` 的花壳。

`wslc` 的这四个命令接口非常干净(单个容器 ID 参数、成功时静默、失败时 stderr + 非零退出码),
适合做成按钮级别的薄封装。

## 实测到的 wslc 行为(3.0.1,作为本规格的依据)

| 命令 | 成功 | 失败 |
|---|---|---|
| `wslc start <id>` | 退出码 0,无输出 | stderr + 非 0 |
| `wslc stop <id>` | 退出码 0,无输出 | stderr + 非 0 |
| `wslc restart <id>` | 退出码 0,无输出 | stderr + 非 0 |
| `wslc remove [-f] <id>` | 退出码 0,无输出 | stderr + 非 0 |

补充事实:

- **幂等**:对"运行中"的容器执行 `start`、对"已停止"的容器执行 `stop`,都返回退出码 0。
  因此应用不需要自己预判状态再决定是否调用,按钮的可用性只是体验优化。
- `restart` 对已停止的容器会直接启动它(CLI 帮助原文:"未运行的容器将启动")。
- `remove` 对**运行中**的容器会失败,错误码 `WSLC_E_CONTAINER_IS_RUNNING`,并提示使用 `-f`。
- `remove` 对不存在的容器失败,错误码 `WSLC_E_CONTAINER_NOT_FOUND`。
- 参数可以传 12 位短 ID(功能 001 中 `wslc list --format json` 的 `ID` 字段就是 12 位)。
- 错误信息一律写在 **stderr**,stdout 为空。
- 失败输出末尾固定带一句样板话:"如果此错误是意外错误,请考虑搜索现有问题或在 … 提交新问题。"

## 预期行为(验收条件)

### AC1 · 命令映射
Core 层必须精确生成下列参数序列(由 `FakeWslcCli.Calls` 断言):

| 操作 | 参数 |
|---|---|
| 启动 | `start <id>` |
| 停止 | `stop <id>` |
| 重启 | `restart <id>` |
| 删除(不强制) | `remove <id>` |
| 删除(强制) | `remove -f <id>` |

`<id>` 一律使用容器的 `ID` 字段,**不使用名称**(名称可能有别名、可能重名)。

### AC2 · 空 ID 防护
`id` 为 null、空字符串或纯空白时,四个方法都抛 `ArgumentException`,且**不产生任何 CLI 调用**。

### AC3 · 失败传播
退出码非 0 时抛 `WslcCliException`,异常消息包含命令名与 stderr 原文(沿用功能 001 的约定)。

### AC4 · 错误文案清洗
UI 展示的错误文本来自 `WslcError.Describe(stderr)`:
去掉空行与"如果此错误是意外错误…"这句样板提示,保留真正的错误描述与 `错误代码:` 行,
多行用空格连接。因此 `找不到容器 'x'。` + `错误代码： WSLC_E_CONTAINER_NOT_FOUND` + 样板行
最终显示为 `找不到容器 'x'。 错误代码： WSLC_E_CONTAINER_NOT_FOUND`。
空 stderr 时返回 `"wslc 命令执行失败。"`。列表刷新失败(功能 001)同样套用这套清洗文案,保证界面里错误风格一致。

### AC5 · 忙碌互斥(全局单操作)
同一时刻整个页面只允许一个生命周期操作在进行:
- 操作开始时,该行 `IsBusy = true`,页面 `IsBusy = true`;
- 期间行内的"启动"键与详情里那四个键全部禁用(其它行同样,页面是全局单操作);
- 操作结束(成功或失败)后恢复。

理由:`wslc` 的容器操作可能耗时数秒,并发发起多个操作会让随后的刷新互相踩踏。

### AC6 · 操作期间暂停刷新
自动刷新循环与手动刷新在 `IsBusy` 为真时直接跳过,不调用 `wslc list`。
避免列表在操作过程中被替换、或用户看到操作前后的中间态。

### AC7 · 成功后刷新一次
操作成功 → 调用一次 `wslc list -a --format json`,列表、汇总数字、"上次刷新时间"随之更新。
删除成功后该容器不再出现在列表中。

### AC8 · 失败不刷新、保留数据
操作失败 → **不**调用 `list`;`Error` 设为清洗后的错误文本(`HasError = true`);
列表数据保持上一次成功加载的内容,`IsBusy` 复位。

### AC9 · 按钮可用性(纯体验,不作为正确性前提)
- 启动:仅"已停止"的容器可用;
- 停止:仅"运行中"的容器可用;
- 重启:始终可用(已停止的会被启动);
- 删除:始终可用(运行中的走强制删除)。

### AC10 · 删除确认属于 UI 层
Core 层不做任何确认。UI 层(ContainersPage)在点击"删除"时弹出 ContentDialog:
- 容器已停止 → 提示"删除容器 <名称>?此操作不可恢复。"
- 容器运行中 → 额外提示"该容器正在运行,将强制停止并删除。",并以 `force: true` 调用。
对话框必须设置 `XamlRoot`,否则 WinUI 3 在非打包模式下抛异常。

### AC11 · 行对象复用
刷新时按容器 `ID` 复用已有的 `ContainerItemViewModel`(只更新其 `Model`),
而不是全部重建。否则每次自动刷新都会让按钮闪断、并丢失 `IsBusy` 状态。

### AC12 · 搜索与过滤仍然纯本地
继承功能 001 AC6:输入搜索词、切换"显示已停止"不产生任何 `wslc` 调用。

## 测试

`tests/wsld.Tests/ContainerActionsTests.cs` 覆盖 AC1–AC8、AC11;
`ContainersPageViewModelTests.cs` 继续覆盖功能 001 的行为,并新增"操作期间跳过刷新"。
所有测试用 `FakeWslcCli` 注入,不需要真实 `wslc`。

## 已知限制

- 不提供 `kill`(强杀)与批量操作:`wslc stop/restart/remove` 本身支持多个 ID,
  但 UI 目前是单行操作,批量留待后续。
- 不暴露 `-t/--time`、`-s/--signal` 停止超时与信号选项。
- 删除时不级联删除匿名卷(`-v`),避免误删数据。
## 验证结果

- 单元/集成测试:60 个全部通过。
- 真实 wslc 端到端(WSLC 3.0.1):生命周期往返通过,包括"运行中删除被 `WSLC_E_CONTAINER_IS_RUNNING` 拒绝"。
- 界面实测:probe1(running)显示绿点、"启动"置灰、"停止/重启/删除"可用;probe2(created)灰点、"停止"置灰、"启动/重启/删除"可用。
